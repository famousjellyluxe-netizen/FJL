TIMELINE VISUALIZATION
════════════════════════════════════════════════════════════════════════════════

STOCK UPDATE (REAL-TIME)
───────────────────────────────────────────────────────────────────────────────
0ms:        Order placed, stock reduced in DB
0-500ms:    Debounce timer running
500ms:      SSE message sent to subscribers
501-502ms:  Clients receive event
502-505ms:  UI updates (buttons, stock badge disabled)
503ms:      localStorage updated with new stock
504-506ms:  Other tabs notified via storage event
506ms:      Other tabs update UI
TOTAL:      <1000ms (typically <500ms)

PRODUCT ADD (CACHE-BASED)
───────────────────────────────────────────────────────────────────────────────
0ms:        Admin creates product
0-20ms:     Saved to database
20-100ms:   Admin sees product immediately
100ms:      Other users see OLD cached list
...
5 min:      Cache expires
5min+100ms: Next user interaction refreshes list
TOTAL:      5-10 minutes

HOW TO SPEED UP SLOW OPERATIONS
════════════════════════════════════════════════════════════════════════════════

Option 1: User Refreshes Browser
─────────────────────────────────────────────────────────────────────────────────
Action:     Ctrl+R (refresh) or Ctrl+Shift+R (hard refresh)
Time:       Immediate
Downside:   Requires user action

Option 2: Clear Cache Manually
─────────────────────────────────────────────────────────────────────────────────
Action:     localStorage.clear() + location.reload()
Time:       Immediate
Downside:   Requires developer knowledge

Option 3: Implement Cache Invalidation
─────────────────────────────────────────────────────────────────────────────────
Action:     Call apiManager.clearCache() after product update
Time:       Next API call (immediate)
Impact:     Changes: productService.js updateProduct() method
Benefit:    Automatic for all users

Option 4: Real-Time via SSE
─────────────────────────────────────────────────────────────────────────────────
Action:     Broadcast product changes via SSE like stock updates
Time:       <1 second
Impact:     Requires backend changes to stockUpdateService.js
Benefit:    Same real-time experience as stock updates

COMMON QUESTIONS
════════════════════════════════════════════════════════════════════════════════

Q: Why is stock update instant but product add is slow?
A: Stock uses Server-Sent Events (real-time streaming).
   Products use HTTP caching (optimized for scale and reducing server load).

Q: Can I make product updates real-time?
A: Yes, with code changes (Option 3 or 4 above). Currently cache-based by design.

Q: What happens if user is offline?
A: Stock updates are queued. When online, they process in order.

Q: How do other browser tabs get notified?
A: Via localStorage storage events detected by DataSyncBus event emitter.

Q: Can I clear the cache?
A: Yes: localStorage.clear() then refresh browser.

Q: Why 5 minutes?
A: Balance between:
   ✓ Fresh data (not too long)
   ✓ Server load (not too often)
   ✓ User experience (acceptable wait)

IMPLEMENTATION NOTES
════════════════════════════════════════════════════════════════════════════════

Current System:
  • 2 Real-time mechanisms: SSE + Polling fallback
  • 3 Cache layers: Backend (memory) + Frontend API + localStorage
  • Cross-tab sync via storage events
  • Offline support via request queuing
  • Automatic cache expiration

Design Principle:
  • Stock = REAL-TIME (critical for inventory)
  • Products = CACHED (can wait 5 minutes)
  • Categories = CACHED (can wait 5 minutes)

Risk Mitigation:
  • No cache invalidation bug (cache expires naturally)
  • SSE has fallback (polling)
  • Offline requests queued (no data loss)
  • Cross-tab sync (all devices stay synced)
